## Beskrivelse

D-110 er lukket, og pull requests står ikke længere i kø bag den fælles lås `e2e-shared-supabase`. Automatiske E2E-tests kører isoleret mod en lokal Supabase-stack og skriver ikke til produktionen. Production Smoke foretager kun de godkendte, skrivebeskyttede kald mod produktionen: GET af site-bundlen og OPTIONS til `get-next-question` og `process-event`. Derudover laver den to read-only kald til GitHub API'et.

D-261 beskriver D3, før den blev merget. Denne fil registrerer afslutningen og beviserne fra de faktiske main-kørsler. D-261 er uændret, fordi registret er append-only.

| Fase | Indhold | Hvor |
|---|---|---|
| A | Isoleret testmiljø: lokal Supabase pr. job, syntetiske konti, commit'ets egne Edge Functions, fail-closed i fem lag med negative kontroller | `isolated-e2e.yml`, D-241 |
| B | Ruleset 26126869 på `~DEFAULT_BRANCH`: `deletion`, `non_fast_forward`, påkrævede checks `unit` + `isolated-e2e (run 1)`, ingen bypass-aktører | D-249 |
| C | Den produktionsrettede E2E kører ikke på pull requests | `playwright.yml` |
| D1 | Isoleret E2E ved push til `main` (PR #468, `beead16`) | `isolated-e2e.yml` |
| D2 | Skrivebeskyttet Production Smoke ved push til `main` (PR #472, `6457af8`) | `production-smoke.yml`, `tools/production-smoke.mjs` |
| D3 | Den produktionsrettede suite kun ved manuel dispatch med `confirm_production` = `production-e2e` (PR #476, `81350e6`) | D-261 |

Den produktionsrettede suite er bevaret, men kører kun ved manuel dispatch og kun med ejerens særskilte GO pr. kørsel. Anledningerne står i D-261 under "Hvornår en manuel produktions-E2E bør køres". `update-avatar-goldens.yml` er uændret og manuel og er den eneste anden bruger af `e2e-shared-supabase`.

**Resterende risici**

Accepterede begrænsninger:
- Ingen automatisk funktionel test af live Edge Functions, produktionens DB/RLS, Auth, udbydere, Worker-runtime og indhold (D-261).
- Ved hurtige main-pushes testes kun den nyeste commit isoleret.
- Production Smoke har ingen timeout pr. request.
- WebKit-flakes i `mobile-ux-validation` klares ved retry.

Næste kendte behov: en manuel produktions-E2E med ejerens GO efter `get-next-question`-deployet og igen efter `LEVEL_ENGINE=v1`. Først sammenlignes den kørende kode med repoet, og deploy og flag kræver hver sit GO.

Mulige forbedringer:
- Bevis cache-skrivning ved cache-miss ved næste runner-image. Det er ikke prøvet i drift og er ikke fremprovokeret.
- Timeout pr. request i Production Smoke.
- Hold øje med kø i den isolerede E2E, når mange sessioner pusher samtidig.
